## Open tensions

Substrate-level (технические, не в whitepaper):
- **OT-1** distributed deletion локальной forever-history у ex-teammates.
- **OT-2** storage compression для forever retention.
- **OT-SEC-2a** (security-hardening Phase 2, deferred) — `uuidStringToRawBytes` silent zero-key fallback (audit HIGH H1) живёт в `DirectMessageService.swift` + `TeamEventBroadcastService.swift` на unmerged Track-5; fix (throw `LeafError.invalidPayload` на битый UUID) откладывается до момента merge Track-5 → `main`, перед тем как код станет «живым». Не remote-triggerable; нет live-exposure пока Track-5 не отгружен. Точный diff — в Phase-2 плане.
- **OT-SEC-3a** (security-hardening Phase 3, deferred) — relay peer-mailbox доступ неаутентифицирован (и чтение-drain, и запись-POST). Чтение: знающий peer pubkey может drain'ить чужой mailbox → metadata leak (timing / частота / размер blob); confidentiality сохранена E2E (AES-GCM). Запись: анонимный POST может заполнить чужой mailbox до cap → таргетированный key-rotation fill-DoS (бот удерживает слоты до TTL). Phase 3 mitigations (server-controlled ordering + per-peer pending cap + per-IP rate-limit) ограничивают blast radius и закрывают lex-order hiding, но НЕ предотвращают distributed targeted flood. Настоящий фикс = write authorization (proof-of-possession под prior team key) — protocol change, затрагивающий всех relay-клиентов. Отложено в отдельный backend-security-audit track. Код: ветка `feature/security-hardening-2026-05-25` в `leaf-relay` (pushed, не merged, не deployed).
